# Архитектура EffectiveTube

## Обзор

EffectiveTube — монолитное веб-приложение с фоновой обработкой медиа. Один образ
содержит и HTTP-слой (FastAPI), и Celery-воркер; инфраструктурные зависимости
вынесены в отдельные контейнеры.

```
                    ┌──────────────────────────────────────────────┐
      Браузер ──────►  app (FastAPI + Jinja2 SSR + JSON API)        │
                    │  /, /watch, /@channel, /upload, /moderation   │
                    │  /api/v1/*  •  /docs (Swagger)                │
                    └───────┬───────────────┬──────────────┬────────┘
                            │               │              │
                    ┌───────▼──────┐ ┌──────▼──────┐ ┌─────▼────────┐
                    │ PostgreSQL 16│ │   Redis 7   │ │ SeaweedFS S3 │
                    │ данные, ACL  │ │ сессии,     │ │ видео,       │
                    │ отчёты, аудит│ │ лимиты,     │ │ превью,      │
                    └──────────────┘ │ очередь     │ │ аватары      │
                                     └──────┬──────┘ └──────▲───────┘
                                            │               │
                                     ┌──────▼───────────────┴──────┐
                                     │ worker (Celery + FFmpeg)    │
                                     │ ffprobe → transcode → jpeg  │
                                     └─────────────────────────────┘
```

## Компоненты

| Компонент | Технология | Ответственность |
|---|---|---|
| `app` | FastAPI 0.115, Uvicorn, Jinja2 | HTTP API, SSR-страницы, стриминг, проверка прав |
| `db` | PostgreSQL 16 | пользователи, видео, комментарии, лайки, плейлисты, жалобы, аудит |
| `redis` | Redis 7 | refresh-token allow-list, rate limit, дедупликация просмотров, очередь Celery |
| `storage` | SeaweedFS (S3 API) | приватные объекты: original, playback, thumbnails, avatars |
| `worker` | Celery 5.7 + FFmpeg | валидация, транскодирование в 720p, извлечение превью |
| `migrate` | Alembic | одноразовый job `alembic upgrade head` до старта app/worker |

## Слои кода

```
app/
  main.py              фабрика приложения, middleware, /healthz, /readyz
  core/                конфиг, JWT/пароли/CSRF, зависимости, Redis
  db/                  declarative base, async engine/session
  models/              SQLAlchemy 2.0 модели (users, videos, social, playlists, moderation)
  schemas/             Pydantic v2 схемы запросов/ответов
  services/            бизнес-логика: доступ, стриминг, сериализация, storage, аудит
  api/v1/              JSON API (auth, videos, channels, playlists, moderation, admin, search)
  web/                 SSR-страницы и Jinja2-окружение
  workers/             Celery app и медиа-пайплайн
  templates/           Jinja2-шаблоны (YouTube-подобный UI, ru)
  static/              CSS/JS/иконки
```

Правило зависимостей: `api`/`web` → `services` → `models`/`db`. Модели не знают
про HTTP, сервисы не знают про шаблоны, шаблоны получают уже сериализованные
словари (`app/services/serializers.py`).

## Поток загрузки

1. `POST /api/v1/videos` создаёт запись со статусом `uploading`.
2. `POST /api/v1/videos/{id}/file` проверяет владельца, размер, MIME и magic
   bytes контейнера, затем потоково кладёт файл в S3 (`raw/...`).
3. Запись переводится в `processing`, Celery получает задачу `videos.process`.
4. Воркер: `ffprobe` (валидация, длительность, кодеки) → `ffmpeg` (remux без
   перекодирования, если H.264/AAC ≤ 720p, иначе transcode в H.264/AAC 720p) →
   JPEG-превью → загрузка `videos/...` и `thumbnails/...` → статус `ready`.
5. Исходный файл удаляется из хранилища после успешной обработки.

Статусы: `uploading → processing → ready | failed`. Ошибка сохраняется в
`failure_reason` и видна владельцу в студии и на странице просмотра.

## Поток просмотра

* `GET /watch/{id}` — SSR-страница; права проверяются до рендера.
* `GET /api/v1/videos/{id}/stream` — проксирование из S3 с поддержкой
  `Range` (`206 Partial Content`), `HEAD`, `Accept-Ranges`. Файлы никогда не
  отдаются напрямую из бакета и не имеют публичных URL.
* `POST /api/v1/videos/{id}/view` — дедуплицированный счётчик (Redis NX на 6
  часов + ledger `view_events`).
* Лайки/дизлайки и комментарии меняют денормализованные счётчики в `videos` в
  той же транзакции.

## Почему так

* **Монолит + воркер** — минимальная операционная сложность при сохранении
  асинхронной обработки видео; ТЗ требует развёртывание одной командой.
* **SSR + прогрессивный JS** — страницы работают без сборки фронтенда и
  остаются доступными при отключённом JS; API при этом полноценный и
  документирован в Swagger.
* **Проксирование медиа** — единственная точка проверки прав; приватные видео
  не утекают через прямые ссылки на хранилище.
* **Денормализация счётчиков** — лента и карточки не делают `COUNT(*)` по
  лайкам/комментариям; значения обновляются в тех же транзакциях.
