# Безопасность

## Аутентификация и сессии

* Пароли — **Argon2id** (`time_cost=3`, `memory_cost=64 MiB`, `parallelism=2`,
  соль 16 байт, хэш 32 байта). Открытый пароль нигде не логируется и не
  сохраняется; при входе выполняется `check_needs_rehash`.
* Политика пароля: 10–128 символов, обязательны буквы и цифры; username — 3–40
  символов `[A-Za-z0-9_.-]`, зарезервированные имена запрещены.
* JWT (HS256): access — 30 минут, refresh — 14 дней. Оба токена в
  `httpOnly`-куках (`SameSite=Lax`, `Secure` при `COOKIE_SECURE=true`).
* Refresh-токены одноразовые: `jti` хранится в Redis allow-list. При каждом
  `/auth/refresh` старый `jti` удаляется, выдаётся новая пара. Повторное
  использование неизвестного `jti` очищает сессию.
* Выход удаляет `jti` из allow-list и все cookie.
* Неверный логин всегда возвращает `401 Invalid credentials`; для
  несуществующего пользователя всё равно проверяется фиктивный Argon2-хэш,
  чтобы не выдавать существование аккаунта по времени ответа.
* Неактивный аккаунт (`is_active=false`) не проходит аутентификацию.

## CSRF

Double-submit cookie: значение из cookie `et_csrf` должно совпадать с заголовком
`X-CSRF-Token`. Проверка выполняется middleware для всех небезопасных
`/api/*`-запросов, аутентифицированных cookie. Исключения — `login`,
`register`, `refresh` (сессии ещё нет). Запросы с `Authorization: Bearer`
освобождены: браузер не добавляет заголовок сам, CSRF невозможен. Сравнение —
`hmac.compare_digest`.

## Заголовки безопасности

`SecurityHeadersMiddleware` добавляет:

* `Content-Security-Policy: default-src 'self'; img-src 'self' data: blob:;
  media-src 'self' blob:; style-src 'self' 'unsafe-inline'; script-src 'self';
  frame-ancestors 'none'; base-uri 'self'; form-action 'self'` — внешние
  скрипты и фреймы запрещены, inline-JS отсутствует;
* `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`,
  `Cross-Origin-Opener-Policy: same-origin`;
* `Strict-Transport-Security` — только при `COOKIE_SECURE=true` (HTTPS).

## Права на видео

Правила сосредоточены в `app/services/access.py`, поэтому API, SSR и стриминг
не могут разойтись.

| Ситуация | Аноним | Владелец | Приглашённый | Модератор | Админ |
|---|---|---|---|---|---|
| public + visible + ready | ✅ | ✅ | ✅ | ✅ | ✅ |
| unlisted + visible + ready | ✅ (по ссылке) | ✅ | ✅ | ✅ | ✅ |
| private | ❌ | ✅ | ✅ | ❌ | ✅ |
| hidden модерацией | ❌ | ✅ | ❌ | ✅ | ✅ |
| removed модерацией | ❌ | ✅ | ❌ | ✅ | ✅ |
| ещё не обработано | просмотр метаданных | ✅ | — | — | ✅ |

* Приватные видео не показываются в ленте, поиске, рекомендациях и на канале.
* Для посторонних недоступное видео отдаёт **404**, а не 403 — нельзя
  подтвердить существование приватного id.
* Управлять видео (редактировать, удалять, выдавать доступ) может владелец и
  администратор; модератор — только скрывать/восстанавливать.
* `video_access_grants` — единственный источник доступа к приватному видео;
  владелец не может выдать доступ самому себе, повторная выдача идемпотентна.

## Загрузка файлов

* Лимит размера — 2 ГиБ (`MAX_UPLOAD_BYTES`), длительность — 4 часа.
* Разрешённые контейнеры: MP4/MOV/WebM/MKV/AVI; проверяются MIME, magic bytes
  (`ftyp`, EBML, RIFF/AVI) и повторно — `ffprobe` в воркере.
* Файл не исполняется и не отдаётся статикой: он лежит в приватном бакете,
  ключ — `raw/<owner>/<hash>.<ext>`; наружу отдаётся только через прокси с
  проверкой прав.
* Публичных presigned URL нет; бакет не публикуется.
* Ошибка обработки сохраняется в `failure_reason`, исходник можно заменить.

## Прочее

* **SQL-инъекции**: SQLAlchemy с bind-параметрами; редкие raw-запросы
  (`view_events`, `watch_history`) используют только именованные параметры.
* **XSS**: Jinja2 autoescape включён; JS вставляет пользовательский текст через
  `textContent`, а не `innerHTML`; CSP запрещает inline-скрипты.
* **Rate limiting**: Redis, фиксированное окно; отдельные лимиты на login (по IP
  и по логину), регистрацию, комментарии, жалобы, загрузку. При недоступности
  Redis защита fail-open с записью в лог, чтобы не уронить сайт.
* **Секреты**: `.env` в `.gitignore`; `deploy.sh` генерирует
  `SECRET_KEY`, пароль БД и S3-ключи через `openssl rand`; файл
  `infra/seaweedfs/s3.json` рендерится из шаблона и не коммитится.
* **Контейнер**: приложение работает от непривилегированного пользователя
  `appuser` (UID 10001), `tini` как init-процесс.
* **Аудит**: действия модераторов и администраторов пишутся в `audit_log`
  (актор, действие, сущность, IP, время).

## Осознанные ограничения демо

* `COOKIE_SECURE=false` при HTTP-развёртывании: для HTTPS поставьте
  `COOKIE_SECURE=true` (и HSTS включится автоматически).
* Нет подтверждения email, 2FA и восстановления пароля — вне рамок тестового
  задания.
* Антивирусная проверка загружаемых файлов не выполняется; допустимые контейнеры
  ограничены, а обработка идёт в отдельном контейнере без доступа к БД хоста.
* Rate limiter доверяет первому значению `X-Forwarded-For`; при развёртывании
  за обратным прокси это ожидаемо, при прямом доступе заголовок можно подделать.
